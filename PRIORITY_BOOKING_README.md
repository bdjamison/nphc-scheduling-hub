# NPHC-HC priority booking — staging candidate
Deploy frontend and API together to staging first. No migration required. Sign in as an approver, choose Request a Space, NPHC-HC, and select rooms. Single-date requests only; recurring requests use the existing ordinary workflow. Room 258 is excluded. Existing NPHC-HC events are protected from automatic displacement (manual resolution). Public users cannot use priority endpoints. Requests do not claim slots until approved. Approval rechecks conflicts and requires confirmation; conflicting individual occurrences are revoked, not entire series. Cancellation emails direct recipients to Bruce Nelson (nphcoperations@gmail.com). Failed notifications are recorded on the revoked row (cancellationNotification); manual follow-up is required. Existing ACS settings must be configured.

Azure Tables cannot transact across partitions/tables. This implementation uses conditional writes and best-effort compensation; a crash or concurrent mutation can leave partial state. Do not deploy to production until staging tests cover concurrent approvals/edits, injected failures, slot ownership and recovery, email delivery, and the courtyard's existing partition mapping. Back up tables first. A priority_processing row or rollback error requires manual reconciliation before retrying. No live tests or full dependency build performed. Existing group approvals create independent room reservations; later edits/revocations are per room.
